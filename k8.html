Learn to run the school kitchen

Kubernetes (people write K8s) is a giant school kitchen that runs lots of apps at once. In three lessons you learn to talk to the kitchen, fix lunch boxes that will not start, and fix pickup windows that nobody can reach.

Set up a practice kitchen (do this first)

Never practice on a real shared cluster. Build a tiny one on your own laptop. It takes about ten minutes.

  1. Install Docker Desktop (or Podman). Your practice cluster runs inside containers, so you need a container engine first.
  2. Install kubectl, the walkie-talkie. Follow the official install tools page for your computer.
  3. Install minikube from the minikube start page, then start the cluster: 
    minikube start
kubectl get nodes
    You should see one node with the status Ready.
  4. Install Helm from the Helm install page, then check it: 
    helm version
  5. Run your first app and look at it: 
    kubectl create namespace web
kubectl create deployment shop --image=nginx:1.27 -n web
kubectl get pods -n web
    When the pod says Running, your kitchen works. You will use this shop app again in Lesson 3.

Lesson 1: Talking to the kitchen

Two tools. kubectl is the walkie-talkie: you ask questions and give orders. Helm is the cookbook: you install a whole meal with one command.

Almost every kubectl command has the same shape: kubectl VERB THING NAME -n NAMESPACE. For example kubectl describe pod my-pod -n web. Learn the shape once and new commands feel familiar.

Part 1: kubectl

1. Check your tools and see the cluster

First make sure the walkie-talkie has batteries. This prints your kubectl version and, if it can reach the cluster, the cluster version too.

kubectl version
kubectl cluster-info
kubectl get nodes

cluster-info tells you if Kubernetes is awake and where the control room is. get nodes lists the computers doing the work. Every node should say Ready.

2. List things with get

get is your best friend. It shows a simple table of things that exist.

kubectl get pods
kubectl get deployments
kubectl get services
kubectl get namespaces

Helpful extras

kubectl get pods -A          # all kitchens (all namespaces)
kubectl get pods -o wide     # extra details, like which node the pod is on
kubectl get pods -n my-app   # only look in one kitchen
kubectl get pods -w          # watch: keep the table open and show changes live

Short names save typing: po = pods, deploy = deployments, svc = services, ns = namespaces. So kubectl get po -A works.

3. Get the full story with describe

describe opens the report card for one thing. It is the most useful command when something is broken.

kubectl describe pod my-pod
kubectl describe deployment my-app
kubectl describe node worker-1

Scroll to the bottom and read Events. Events are short notes from Kubernetes about what it tried and what went wrong. They often say exactly why a pod is stuck.

4. Create or update from a file with apply

apply reads a YAML file and makes the cluster match it. If the thing is new, it creates it. If it already exists, it updates it. Most teams use this every day.

kubectl apply -f app.yaml

create is similar, but it fails if the thing already exists. Prefer apply.

5. Delete things 
kubectl delete pod my-pod
kubectl delete deployment my-app
kubectl delete -f app.yaml
Deleting a namespace deletes everything inside it. Read the command twice before you press Enter.

Surprise: if a Deployment owns a pod and you delete the pod, a new pod appears a few seconds later. The recipe says “keep 3,” so Kubernetes cooks a replacement. To really remove the app, delete the Deployment.

6. Read the app’s diary with logs

logs prints whatever the app printed inside its container.

kubectl logs my-pod
kubectl logs -f my-pod                 # -f = follow, like a live chat
kubectl logs my-pod -c my-container    # pick one container in a multi-container pod
kubectl logs my-pod --previous         # the diary of the container that died (Lesson 2)
7. Climb inside a pod with exec

exec runs a command inside the running lunch box. Good for checking files or testing a connection.

kubectl exec -it my-pod -- bash
kubectl exec -it my-pod -- sh      # if bash is not installed

-it means “interactive, with a terminal,” so you can type. The -- tells kubectl “everything after this is the command to run inside.”

8. Make more copies with scale 
kubectl scale deployment my-app --replicas=3

Now Kubernetes tries to keep 3 pods ready. If one dies, it makes another.

Best practice: scale is great for practice and emergencies. For real work, change replicas: in the YAML file and apply it, so the file and the cluster always agree.
9. Watch or undo an update with rollout

A rolling update brings new pods in while old pods go out, so the app never fully stops.

kubectl rollout status deployment/my-app
kubectl rollout history deployment/my-app
kubectl rollout undo deployment/my-app
kubectl rollout restart deployment/my-app

undo is the “oops, go back” button. restart replaces every pod one by one with a fresh copy, which is handy after you change a ConfigMap or Secret.

10. Make a secret tunnel with port-forward 
kubectl port-forward pod/my-pod 8080:80
kubectl port-forward svc/my-service 8080:80

The numbers are LAPTOP_PORT:POD_PORT. Now open http://localhost:8080 on your computer. The tunnel lasts until you press Ctrl+C. It is for testing only, not for real visitors.

11. Switch kitchens and clusters 
kubectl config get-contexts
kubectl config use-context my-cluster
kubectl config set-context --current --namespace=dev

A context is a saved combo of cluster + user + default namespace. The star in get-contexts shows where your walkie-talkie is pointed right now.

Before any delete, run kubectl config current-context. Many real accidents are a correct command sent to the wrong cluster.

Part 2: Helm

Helm talks in three words. A chart is the cookbook recipe. A release is one cooked meal made from that recipe. A repo is a library of cookbooks on the internet.

1. Check Helm and add a cookbook library 
helm version
helm repo add bitnami https://charts.bitnami.com/bitnami
helm repo update
helm repo list
helm search repo nginx

repo add tells Helm where to find charts. repo update refreshes the list of recipes. search repo looks through the libraries you added. To search charts from everyone, use Artifact Hub.

2. Install an app 
helm install my-web bitnami/nginx

The shape is helm install RELEASE_NAME CHART. You choose the release name. Install into a specific kitchen and create it if needed:

helm install my-web bitnami/nginx -n web --create-namespace

Use your own settings

helm install my-web bitnami/nginx -f values.yaml
helm install my-web bitnami/nginx --set replicaCount=3

Practice first without changing the cluster

helm install my-web bitnami/nginx --dry-run=client --debug
3. See what is installed 
helm list
helm list -A
helm status my-web

Like kubectl, Helm only looks in your current namespace unless you add -n NAME or -A. “My release vanished” usually means “I am in the wrong kitchen.”

4. Upgrade, roll back, and remove 
helm upgrade my-web bitnami/nginx -f values.yaml
helm upgrade --install my-web bitnami/nginx -f values.yaml

upgrade --install means “install it if it is missing, upgrade it if it is there.” Teams love it because one command always works.

helm history my-web
helm rollback my-web 1
helm uninstall my-web

Every install or upgrade makes a new numbered revision. rollback my-web 1 goes back to revision 1. uninstall removes everything the release created.

5. Make, check, and peek 
helm create my-chart
helm lint my-chart
helm template my-web ./my-chart
  • create builds a starter recipe folder
  • lint checks it for mistakes
  • template shows the YAML Helm would send to Kubernetes, without installing anything
helm show values bitnami/nginx    # the recipe's default settings
helm get values my-web            # the settings YOUR installed release uses

Helm does not replace kubectl. Helm packages apps. kubectl still inspects pods, logs, and problems.

Tutor tips

  1. Always start with kubectl get pods or kubectl get pods -A.
  2. If a pod is not Running, use kubectl describe pod NAME first, then kubectl logs NAME.
  3. Practice in a practice cluster. Do not delete things in a shared cluster unless a teacher says so.
  4. Namespaces matter. If you “can’t find” a pod, you may be in the wrong kitchen. Try -A or -n.
  5. apply is safer for daily work than guessing between create and update.

Lesson 2: Lunch boxes that will not start

Three statuses scare people the most. Each one tells you how far the pod got before it failed.

Rule #1: the status is a clue, not the answer. Your job is to find the reason under the status.
The detective kit (use it every time, in order) 
kubectl get pods -A
kubectl describe pod POD_NAME -n NAMESPACE
kubectl logs POD_NAME -n NAMESPACE
kubectl logs POD_NAME -n NAMESPACE --previous
kubectl get events -n NAMESPACE --sort-by=.lastTimestamp
CommandWhat it tells you
get podsWhich status? How many restarts?
describe podEvents and last exit reason. Best first deep look.
logsWhat the app printed this run
logs --previousWhat the app printed the run that crashed
get eventsCluster timeline around the failure

Tutor tip: for Pending and ImagePullBackOff, describe Events usually wins. For CrashLoopBackOff, logs --previous usually wins.

Case 1: Pending

Plain English: the pod is waiting in line. Kubernetes has not picked a node for it yet. The app has not started, so logs are empty. That is normal.

kubectl get pod shop-abc123 -n web
kubectl describe pod shop-abc123 -n web

Scroll to Events and look for FailedScheduling. The message tells you which of these five problems you have.

1. Not enough CPU or memory

0/3 nodes are available: 3 Insufficient cpu
0/3 nodes are available: 3 Insufficient memory

The pod asked for more CPU or RAM than any node has free. Check the nodes:

kubectl get nodes
kubectl describe node NODE_NAME      # look at "Allocated resources"
kubectl top nodes                    # needs metrics-server installed

Fixes: lower the pod’s resources.requests if they are too greedy, free space by deleting unused pods, or ask the teacher or cloud team to add nodes.

Important: Kubernetes schedules using requests, not how much the app might use later.

2. Taints (the “keep out” sign)

0/3 nodes are available: 3 node(s) had untolerated taint

A node can say “only special pods sit here.” If your pod has no matching toleration, it stays Pending.

kubectl describe nodes | grep Taints

Fixes: add a toleration to the pod, use a different node, or a teacher removes the taint. Never remove taints on a shared cluster without permission.

3. Wrong node label or nodeSelector

0/3 nodes are available: 3 node(s) didn't match Pod's node affinity/selector

The recipe said “only sit at tables labeled disk=ssd,” but no table has that label.

kubectl get nodes --show-labels

4. Storage is not ready (PVC)

pod has unbound immediate PersistentVolumeClaims

The pod wants a saved backpack (a volume), but that backpack does not exist yet.

kubectl get pvc -n web
kubectl describe pvc CLAIM_NAME -n web

If the PVC is also Pending, fix storage first. The pod will wait forever otherwise.

5. Namespace quota is full

exceeded quota

The kitchen has a class limit like “this namespace may only use 2 CPU.” Your pod would break the rule.

kubectl describe resourcequota -n web
Pending cheat card: Pending = scheduler problem. Do not start with logs. Start with describe Events.
Case 2: ImagePullBackOff (and ErrImagePull)

Plain English: Kubernetes found a node, tried to download the container image, and failed. It waits longer before each new try. BackOff means “I’ll try again later, slower.”

ErrImagePull is the failed pull. ImagePullBackOff is Kubernetes pausing before the next try. Same problem, two moments.

kubectl describe pod shop-abc123 -n web

Events often say Failed to pull image, manifest unknown, unauthorized, authentication required, or not found.

Common causes

  1. Typo in the image name or tag. ngnix instead of nginx. myapp:v2 when only myapp:v1 exists. latest when that tag was never pushed.
  2. Private registry, missing password. Private images need a pull secret, and the pod must point at it: 
    imagePullSecrets:
  - name: regcred
  3. The cluster cannot reach the registry. School firewall, no internet on the nodes, or a wrong registry URL.
  4. Rate limits. Public Docker Hub sometimes says “too many downloads.” That looks like a pull failure.

Useful checks

kubectl get pod shop-abc123 -n web -o yaml | grep image:
kubectl get secrets -n web
docker pull IMAGE_NAME:TAG      # test from your laptop

If your laptop also fails, the image name or tag is probably wrong. If your laptop works but the cluster fails, it is often auth or network.

ImagePullBackOff cheat card: the container never started, so app logs are empty. Fix the image name, tag, or pull secret.
Case 3: CrashLoopBackOff

Plain English: the image did download. The container did start. Then the process inside quit. Kubernetes restarts it, it fails again, and Kubernetes waits longer between tries. This is an app or config problem more often than a cluster problem.

kubectl get pod shop-abc123 -n web
kubectl describe pod shop-abc123 -n web
kubectl logs shop-abc123 -n web --previous
kubectl logs shop-abc123 -n web -c CONTAINER_NAME --previous

Why --previous? The current container may have just restarted and printed nothing yet. The last dead container usually holds the real error.

What to read in describe

State:          Waiting
  Reason:       CrashLoopBackOff
Last State:     Terminated
  Reason:       Error
  Exit Code:    1
Restart Count:  8

Exit codes to know

Exit codeUsual meaningWhere to look
0Process finished “successfully” and leftThe command; servers should keep running
1App error (bad config, missing file, crash)logs
126Command cannot run (permissions)command / image
127Command not foundcommand spelling
137Killed hard (SIGKILL), very often OOMKilledmemory limit
139Segfault (app or library bug)app or base image
143SIGTERM (asked to stop)often a shutdown, not always a bug

Common CrashLoop causes

  1. The app is broken or missing settings. Logs say things like Cannot connect to database, KEY not set, or No such file or directory. Check that ConfigMaps and Secrets exist: 
    kubectl get configmap -n web
kubectl get secret -n web
  2. OOMKilled. Last State reason OOMKilled, exit code 137. The app used more RAM than resources.limits.memory. Fix the leak or raise the limit (with a teacher’s okay).
  3. Liveness probe is too strict. Kubernetes thinks the app is dead and kills it, even if it is just slow to start. Events show Liveness probe failed then Killing. Give the app more initialDelaySeconds, fix the health URL, or better, add a startup probe.
  4. The container command finishes. A server should keep running. If the command is echo hello, it prints, exits 0, and Kubernetes restarts it. Loop.
  5. An init container failed. The main app never starts because a helper container failed first: 
    kubectl logs shop-abc123 -n web -c INIT_CONTAINER_NAME
CrashLoop cheat card: image pulled, process dies. describe for the exit code. logs --previous for the story.
Look-alikes: do not mix these up
  • CreateContainerConfigError: a Secret or ConfigMap key is missing, so the container cannot even be set up.
  • OOMKilled: often seen inside a CrashLoop. It is the reason, CrashLoopBackOff is the status.
  • Evicted: the node ran out of disk or memory and kicked the pod off.
  • Init:CrashLoopBackOff: same loop, but in an init container.
A 5-minute classroom flow
  1. kubectl get pods -n web. Read STATUS and RESTARTS.
  2. If Pending or ImagePullBackOff: describe, read Events, stop guessing.
  3. If CrashLoopBackOff: describe for Last State and exit code, then logs --previous.
  4. Fix the cause, not the status. Deleting the pod over and over does not fix a typo in the image name.
  5. After a fix: kubectl get pods -w and watch it become Running.

Official references: Debug Pods, Debug Running Pods, Pod Lifecycle, Images.

Lesson 3: The pickup window nobody can reach

Every pod says Running. The Service exists. And still, nothing connects. This is the sneakiest kind of broken, because no status turns red. You have to follow the path yourself.

The path of one request

When the cart app calls http://shop, four things must work, in this order. A break at any link stops everything.

LinkKitchen pictureWhat really happensWhat breaks it
1. DNSLook up the window in the school directoryThe name shop turns into the Service’s IP addressWrong name, wrong namespace, DNS pods down
2. SelectorThe window checks stickers to find its lunch boxesThe Service finds pods whose labels match its selectorLabel typo: zero pods match
3. ReadyOnly lunch boxes that say “ready to serve” go on the window listOnly pods passing their readiness probe become endpointsProbe fails: pod is Running but not on the list
4. PortKnock on the right door of the lunch boxService port forwards to the pod’s targetPorttargetPort is not where the app listens
Step-by-step lab: build a working Service, break it, fix it

Do this in your practice cluster. You will see a healthy Service first, so you know what “good” looks like.

  1. Make the app (skip the namespace line if you did it on the Start page): 
    kubectl create namespace web
kubectl create deployment shop --image=nginx:1.27 --replicas=2 -n web
  2. Make the pickup window. expose writes a Service whose selector matches the Deployment’s labels: 
    kubectl expose deployment shop --port=80 --target-port=80 -n web
  3. Look at the healthy picture: 
    kubectl get svc,pods -n web -o wide
kubectl describe svc shop -n web
    In describe, find Selector: app=shop and an Endpoints: line with two IP addresses. Two pods, two addresses. That is the window’s list of lunch boxes.
  4. Test from inside the cluster with a throwaway pod: 
    kubectl run tester --rm -it --restart=Never --image=busybox:1.36 -n web -- wget -qO- http://shop
    You should see the “Welcome to nginx” page. --rm deletes the tester when it finishes.
  5. Break it on purpose. Change the selector to a typo: 
    kubectl patch svc shop -n web -p '{"spec":{"selector":{"app":"shopp"}}}'
  6. See the sneaky failure: 
    kubectl get svc,pods -n web
kubectl describe svc shop -n web
    The Service is still there. The pods still say Running. But Endpoints: is now <none>, and the wget test from step 4 fails.
  7. Fix it and test again: 
    kubectl patch svc shop -n web -p '{"spec":{"selector":{"app":"shop"}}}'
You just learned the most important line in this lesson: Endpoints: <none> means the window has no lunch boxes behind it.
The Service detective kit

Work from the Service toward the pod. Stop at the first thing that looks wrong.

# 1. Does the Service exist? What are its selector and ports?
kubectl get svc shop -n web -o wide
kubectl describe svc shop -n web

# 2. Does it have any pods behind it?
kubectl get endpointslices -n web -l kubernetes.io/service-name=shop

# 3. Which pods SHOULD match? Use the Service's own selector.
kubectl get pods -n web -l app=shop -o wide
kubectl get pods -n web --show-labels

# 4. Test from inside the cluster
kubectl run tester --rm -it --restart=Never --image=busybox:1.36 -n web -- sh
#    then, inside: nslookup shop   and   wget -qO- http://shop

Case 1: The selector does not match (stickers are wrong)

Plain English: a Service does not know pods by name. It looks for pods wearing the right label stickers. If the Service says app: shop and the pods say app: shop-v2, the Service finds nobody. Kubernetes does not warn you. An empty Service is perfectly legal.

The three places that must agree

# Deployment
spec:
  selector:
    matchLabels:
      app: shop          # (A) the Deployment finds its own pods with this
  template:
    metadata:
      labels:
        app: shop        # (B) the sticker put on every pod
---
# Service
spec:
  selector:
    app: shop            # (C) the Service looks for this sticker

(B) and (C) must match exactly. Same key, same value, same capital letters. App: shop is not app: shop.

Prove it

kubectl describe svc shop -n web | grep -i selector
kubectl get pods -n web -l app=shop        # paste the selector here

If the second command says No resources found, you found the bug. Fix the label or the selector in the YAML (or Helm values), then apply.

If a Service has two selector labels, a pod must have both. Selectors mean AND, never OR.
Case 2: Pods are Running but not Ready (readiness probe)

Plain English: Running means the process started. Ready means “I can serve customers now.” A Service only sends traffic to Ready pods. Look at the READY column:

NAME              READY   STATUS    RESTARTS
shop-84c6-lm3nd   0/1     Running   0

0/1 means zero of one containers are ready. The labels match, but the pod is kept off the window’s list until its readiness probe passes.

kubectl describe pod shop-84c6-lm3nd -n web

Events will say something like Readiness probe failed: HTTP probe failed with statuscode: 404 or connection refused.

Common reasons

  • The probe checks the wrong path (/healthz when the app has /health).
  • The probe checks the wrong port.
  • The app truly is not ready, for example it cannot reach its database. Read kubectl logs.
  • The timeoutSeconds is shorter than the app’s answer time.
readinessProbe:
  httpGet:
    path: /health
    port: 8080
  periodSeconds: 5
  failureThreshold: 3
ProbeQuestion it asksIf it fails
StartupHave you finished booting?Other probes wait. Fails too long: container restarts.
LivenessAre you stuck or dead?Container is restarted (can cause CrashLoop, Lesson 2)
ReadinessCan you take customers right now?Pod is removed from the Service. No restart.
Case 3: Wrong port (knocking on the wrong door)

A Service has up to three port numbers, and people mix them up all the time.

FieldWhereMeaning
portServiceThe door number on the window. Clients call this.
targetPortServiceThe door number on the lunch box. Must be where the app really listens.
containerPortPodA label for humans. It does not open or close anything.
 
ports:
  - port: 80           # clients call http://shop:80
    targetPort: 8080   # traffic is sent to the pod on 8080

If the app listens on 3000 but targetPort says 8080, endpoints look perfect and every call gets connection refused.

Prove it: skip the Service and call the pod directly

kubectl get pods -n web -o wide                      # copy a pod IP
kubectl run tester --rm -it --restart=Never --image=busybox:1.36 -n web -- wget -qO- http://POD_IP:3000
kubectl port-forward pod/shop-84c6-lm3nd 8080:3000 -n web

If the pod answers on 3000 directly but the Service fails, the Service’s targetPort is wrong.

Sneaky cousin: the app listens on 127.0.0.1 (localhost) only. Then it answers inside its own container but refuses everyone else, including the Service. Apps in containers should listen on 0.0.0.0.
Case 4: DNS (the name does not turn into an address)

Plain English: the cluster has its own phone book, run by pods called CoreDNS. Every Service gets a name in it automatically.

You typeWorks from
shopOnly pods in the same namespace
shop.webAny namespace
shop.web.svc.cluster.localAny namespace (the full name)

The pattern is SERVICE.NAMESPACE.svc.cluster.local. The number one DNS “bug” is calling shop from a different namespace.

Test it

kubectl run tester --rm -it --restart=Never --image=busybox:1.36 -n tools -- nslookup shop.web
kubectl exec -it my-pod -n tools -- cat /etc/resolv.conf

If every name fails, check the phone book itself

kubectl get pods -n kube-system -l k8s-app=kube-dns
kubectl logs -n kube-system -l k8s-app=kube-dns
kubectl get svc kube-dns -n kube-system

The CoreDNS pods should be Running and 1/1. If they are broken on a shared cluster, tell a teacher. Do not fix kube-system yourself.

DNS names point at Services, not Deployments. If you made a Deployment called shop but never made a Service, http://shop will not resolve.
Case 5: You are calling from the wrong place, or a rule blocks you

ClusterIP from your laptop

The default Service type is ClusterIP. Its address only exists inside the cluster. Typing it into your laptop browser will hang forever. For testing, tunnel in:

kubectl port-forward svc/shop 8080:80 -n web

For real visitors, you need a NodePort, a LoadBalancer, or an Ingress / Gateway. See the “Service types” popup at the top of this lesson.

NetworkPolicy

A NetworkPolicy is a hall-pass rule: “only pods from these places may talk to these pods.” If DNS works, endpoints are full, the port is right, and calls still time out, look for one:

kubectl get networkpolicy -n web
kubectl describe networkpolicy -n web
The 5-minute Service flow and cheat card
  1. kubectl get pods -n web. Is READY 1/1? If 0/1, go to Case 2.
  2. kubectl describe svc shop -n web. Is Endpoints empty? If yes and pods are Ready, go to Case 1.
  3. Endpoints exist? Compare TargetPort with the port the app really listens on. Case 3.
  4. Test from a tester pod. bad address? Case 4. Timeout? Case 5.
  5. Fix the YAML or Helm values, apply or helm upgrade, test again.

Best practices so this never happens

  • Use the standard label app.kubernetes.io/name everywhere, and let Helm fill it in from one value so the three places cannot drift apart.
  • Give container ports a name and point targetPort at the name.
  • Always add a readiness probe to anything that sits behind a Service.
  • Call other namespaces as service.namespace.

Lesson 1

Common kubectl and Helm commands

Think of Kubernetes (K8s) as a giant school kitchen that runs many apps at once. kubectl is the walkie-talkie you use to talk to that kitchen. Helm is a cookbook: one command can install a whole meal instead of writing every recipe line yourself.

Kitchen wordK8s wordWhat it is
Lunch boxPodOne running app (usually one or more containers)
Recipe that keeps 3 boxes readyDeploymentKeeps the right number of pods alive
Pickup window numberServiceStable way to reach a changing set of pods
Separate kitchenNamespaceA named room so teams do not mix their stuff
Cookbook recipeHelm chartPackaged YAML + default settings
One cooked mealHelm releaseOne installed copy of a chart

Step 1 · Check your tools

Before you cook, check the oven. These commands only look. They do not change the cluster.

kubectl version
kubectl cluster-info
kubectl get nodes
helm version

If get nodes fails, your walkie-talkie is not connected to a cluster yet. That is a config problem, not an app problem.

Step 2 · List things with get

kubectl get is the command you will use most. It prints a simple table.

kubectl get pods
kubectl get deployments
kubectl get services
kubectl get namespaces

kubectl get pods -A
kubectl get pods -o wide
kubectl get pods -n my-app
  • -A or --all-namespaces = look in every kitchen.
  • -n = look in one kitchen only.
  • -o wide = extra columns, like which node a pod sits on.

Short names: po, deploy, svc, ns.

Step 3 · Read the report card with describe

kubectl describe pod my-pod
kubectl describe deployment my-app
kubectl describe service my-svc

Always scroll to Events at the bottom. Events are the kitchen’s diary of what just happened.

Step 4 · Create, update, delete

kubectl apply -f app.yaml
kubectl delete pod my-pod
kubectl delete -f app.yaml
kubectl scale deployment my-app --replicas=3

apply is the daily tool: if the thing is missing, it creates it. If it exists, it updates it. create often fails when the thing already exists.

Step 5 · Logs, exec, port-forward, rollout

kubectl logs my-pod
kubectl logs -f my-pod
kubectl logs my-pod --previous
kubectl exec -it my-pod -- sh
kubectl port-forward pod/my-pod 8080:80
kubectl rollout status deployment/my-app
kubectl rollout undo deployment/my-app
  • -f follows logs like a live chat.
  • --previous is the last crashed container’s diary.
  • exec climbs inside the lunch box.
  • port-forward builds a secret tunnel to your laptop.
  • rollout undo is the oops button for a Deployment.

Step 6 · Helm: the cookbook

helm repo add bitnami https://charts.bitnami.com/bitnami
helm repo update
helm search repo nginx
helm install my-web bitnami/nginx -n web --create-namespace
helm list -A
helm status my-web
helm upgrade --install my-web bitnami/nginx -f values.yaml
helm history my-web
helm rollback my-web 1
helm uninstall my-web
helm create my-chart
helm lint my-chart
helm template my-web ./my-chart --dry-run

Helm does not replace kubectl. Helm packages apps. You still use kubectl to look at pods, logs, and problems.

Tutor memory trick

Look = kubectl get / helm list. Why = describe / status. Put in = apply / install. Change = apply or scale / upgrade. Undo = rollout undo / rollback.

Lesson 2

Troubleshooting broken pods

The status name is a clue, not the answer. Your job is to find the reason under the status. Do not smash kubectl delete pod in a panic loop.

The detective kit (every time)

kubectl get pods -A
kubectl describe pod POD -n NS
kubectl logs POD -n NS
kubectl logs POD -n NS --previous
kubectl get events -n NS --sort-by=.lastTimestamp
StatusDid a node get chosen?Did the image download?Did the app start?First deep look
PendingNoNoNodescribe Events
ImagePullBackOffYesNoNodescribe Events
CrashLoopBackOffYesYesYes, then dieddescribe + logs --previous

Case A · Pending

The pod is still in line. Kubernetes has not picked a computer for it. Logs are often empty. That is normal.

Read Events for FailedScheduling.

  • Insufficient cpu / memory — the pod asked for more than any node has free. The scheduler uses requests, not later real use.
  • Untolerated taint — a node has a keep-out sign and this pod has no matching toleration.
  • nodeSelector / affinity — the recipe asked for a label no node has.
  • Unbound PVC — the saved backpack (volume) is not ready, so the pod waits.
  • Quota — the namespace already used its class limit.
kubectl describe pod shop -n web
kubectl describe node worker-1
kubectl get pvc -n web
kubectl get nodes --show-labels
kubectl describe resourcequota -n web

Case B · ImagePullBackOff

A node was chosen. The image download failed. Kubernetes waits longer each try (that is the BackOff). The app never started, so app logs are usually empty.

  • Typo: ngnix instead of nginx, or a tag that was never pushed.
  • Private registry with no pull secret.
  • Nodes cannot reach the registry (firewall / no internet).
  • Registry rate limit.
kubectl describe pod shop -n web
kubectl get pod shop -n web -o yaml | grep image:
kubectl get secrets -n web

If your laptop can docker pull the image but the cluster cannot, think auth or network, not a typo.

Case C · CrashLoopBackOff

The image downloaded. The process started, then quit. Kubernetes restarts it and waits longer between tries.

kubectl describe pod shop -n web
kubectl logs shop -n web --previous
kubectl logs shop -n web -c CONTAINER --previous

In describe, read Last State and the Exit Code.

ExitUsual meaning
1App error: bad config, missing file, crash
126 / 127Cannot run command / command not found
137OOMKilled — hit the memory limit
139Segfault — app or library bug
0Process finished “successfully” and left. Servers should stay running.

Also watch for a mean liveness probe that kills a slow starter, and for a failed init container.

Lesson 3

Services that look fine but nothing connects

This is the “the phone number exists, but nobody picks up” lesson. Students get stuck here because kubectl get svc is green while the app still fails in the browser.

Background · What a Service really is

Pods die and come back with new IP addresses. You cannot tattoo last week’s pod IP on the cafeteria wall. A Service is a stable front-desk number. Kubernetes keeps a living list of which pods are allowed to answer that number.

That living list is called Endpoints (today often EndpointSlices). If the list is empty, the number rings into an empty room.

Background · Labels are name tags

Every pod can wear stickers: app=shop, tier=frontend. A Service selector is a rule like “send work only to pods wearing app=shop.”

If the stickers do not match the rule — even by one letter — the Service has zero endpoints. The Service object still exists. That tricks people.

# Service wants this sticker:
selector:
  app: shop

# Pod actually wears this sticker:
labels:
  app: Shop          # capital S = different sticker

Background · Ports are two doors

  • port — the door number on the Service (what callers dial).
  • targetPort — the door number on the pod (where the app listens).
  • containerPort — should match what the app really listens on.

A classic miss: Service port: 80 and targetPort: 80, but the app listens on 8080. The Service looks perfect. Traffic hits the wrong door.

Background · Readiness is the “open for business” sign

Three health checks students mix up:

  • Liveness — “Are you still alive?” Fail enough times and Kubernetes restarts the container.
  • Readiness — “Can you take customers right now?” Fail and Kubernetes removes you from the Service. The pod can still be Running.
  • Startup — “Give this slow app time to boot before you judge it.”

So a pod can be Running and still missing from Endpoints because readiness failed. That is why “the pod looks fine” is not enough.

Background · DNS names inside the cluster

From another pod in the same namespace you can often use just the Service name:

shop
shop.web.svc.cluster.local

The long name means: service shop, namespace web, then the cluster domain. If your client pod is in default and the Service is in web, the short name shop will not find it. Use the long name, or put them in the same namespace.

Your laptop is outside the cluster. Cluster DNS names do not work in Chrome on your laptop unless you use port-forward, Ingress, or a LoadBalancer.

Step-by-step · Debug a silent Service

  1. See the Service.

    kubectl get svc -n web
kubectl describe svc shop -n web

    Copy the Selector, Port, and TargetPort.

  2. See who is on the call list.

    kubectl get endpoints shop -n web
kubectl get endpointslices -l kubernetes.io/service-name=shop -n web

    Empty list? The Service is a number with no staff.

  3. See which pods wear the selector stickers.

    kubectl get pods -n web --show-labels
kubectl get pods -n web -l app=shop

    If this list is empty, fix labels. Do not blame DNS yet.

  4. Check Ready, not just Running.

    kubectl get pods -n web
kubectl describe pod POD -n web

    Look at READY 0/1 and Events for failed readiness probes.

  5. Check ports.

    Does targetPort match the app’s listen port? A wrong targetPort can still show endpoints, but traffic dies at the door.

  6. Test from inside the cluster.

    kubectl run tmp --rm -it --restart=Never --image=busybox:1.36 -n web -- sh
# inside that shell:
nslookup shop
nslookup shop.web.svc.cluster.local
wget -qO- http://shop:80/

    If DNS works and HTTP fails, the name is fine. The app, port, or readiness is the problem.

  7. Test one pod directly.

    kubectl port-forward pod/POD 8080:8080 -n web

    If the pod works but the Service does not, the bug is the Service path (selector, endpoints, kube-proxy), not the app code.

  8. Last doors students forget.

    • App listening only on 127.0.0.1 instead of 0.0.0.0.
    • NetworkPolicy blocking the client namespace.
    • Wrong Service type: ClusterIP is only inside the cluster.
    • Calling the Service from your laptop without Ingress / port-forward / LoadBalancer.

Tutor rule

Service exists ≠ traffic works. Ask: “Who is on the Endpoints list, are they Ready, and is the targetPort the real door?”

Picture of the kitchen

Cluster = whole school. Node = a room with ovens. Pod = a lunch box in a room. Deployment = “keep three of these boxes.” Service = the pickup window number. Helm release = a meal cooked from a cookbook. Namespace = one team’s kitchen so soups do not mix.

More on the kitchen words

A container is the food inside the lunch box. A pod can hold more than one container that must sit together (app + helper). Replica means copy. Context is which school kitchen your walkie-talkie is aimed at. YAML files are written recipes kubectl can apply.

More get examples

kubectl get po -A -o wide
kubectl get deploy,svc -n web
kubectl get pods -l app=shop
kubectl get pod shop-abc -o yaml
kubectl config get-contexts

If you “cannot find” a pod, you may be in the wrong namespace. Try -A.

apply vs create vs delete

apply -f is GitOps-friendly and safe to run again. create -f is “make this new thing.” delete namespace can wipe everything inside that kitchen. Practice deletes only in a lab.

More Helm examples

helm install my-web bitnami/nginx --set replicaCount=3
helm install my-web bitnami/nginx --dry-run --debug
helm get values my-web
helm show values bitnami/nginx

--dry-run --debug practices without changing the cluster. upgrade --install creates the release if it is missing.

Why the detective order matters

Pending and ImagePull pods often have no useful app logs. Describe Events speak first. CrashLoop pods often have empty current logs because the new container just started — that is why --previous exists.

Pending examples

Event: 0/3 nodes are available: 3 Insufficient memory. Meaning: every node is too full for this pod’s memory request. Fix: lower requests, free pods, or add nodes.

Event: unbound immediate PersistentVolumeClaims. Check kubectl get pvc. If the PVC is Pending, fix storage first.

Image pull examples

manifest unknown usually means the tag does not exist. unauthorized means the cluster is not logged in. Create a docker-registry secret and set imagePullSecrets on the pod or service account.

CrashLoop examples

Exit 137 + Reason OOMKilled: raise memory limit or fix a leak. Probe events + “Killing”: give a larger initialDelaySeconds or fix the health URL. Command echo hello exits 0 and loops — that belongs in a Job, not a Deployment.

Service types in plain words

ClusterIP (default): only phones inside the school work. NodePort: also opens a high door number on each node. LoadBalancer: cloud gives you a public pickup number. ExternalName: a DNS alias, not a proxy to pods.

Label matching examples

Selector app=shop,tier=front needs BOTH stickers. A pod with only app=shop will not join. Test with kubectl get pods -l app=shop,tier=front. If that command prints nothing, the Service will have empty endpoints.

Probe examples

Readiness HTTP GET /ready on port 8080 fails because the app serves /healthz only. Pod stays Running. Service endpoints stay empty. Fix the path, not the Service name.

Liveness hitting a slow page can restart a healthy-but-busy app and cause CrashLoopBackOff. That is a probe bug, not always an app bug.

Worked example: empty endpoints

1. get svc shop works. 2. get endpoints shop shows <none>. 3. describe says selector app=shop. 4. get pods --show-labels shows app=store. 5. Change the Deployment labels or the Service selector so they match. 6. Endpoints fill. 7. Then test DNS and the port.
